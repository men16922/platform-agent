> 로컬 LLM 에이전트가 자연어 요청 한 문장으로 테넌트의 격리 경계를 만들고, 필요한 애드온을 설치한 뒤, 실제 상태까지 검증할 수 있는가?

맥북 한 대에 로컬 kind 클러스터를 띄웠다. 클라우드 API와 유료 클라우드 리소스는 쓰지 않았다. 아래 수치와 상태는 모두 이 환경에서 직접 측정한 값이다.

영상은 Local Qwen의 테넌트 구성부터 ArgoCD와 대시보드 검증까지 이어진다. 마지막에는 NetworkPolicy를 일부러 제거했다. 대시보드의 network 축만 실패로 바뀌는지 본 다음 정책을 복구해 정상 상태로 돌아오는 것까지 확인했다. 재생 속도는 그대로 두고 대기 구간만 잘라냈다.

## 실험 목표

기존 자동화는 클러스터와 애플리케이션을 만들었지만 “이 클러스터가 누구의 환경인지”까지는 다루지 못했다. 자연어 요청은 다음 두 단계로 이어진다.

```text
setup_tenancy
→ Namespace · ResourceQuota · NetworkPolicy · RBAC · Pod Security 구성

install_tenant_addons
→ 레지스트리에 선언된 Loki · Tempo 설치
```

테넌트 경계를 먼저 만들고 그 안에 애드온을 설치해야 한다. 순서를 바꾸면 애드온이 들어갈 Namespace와 보안 정책이 없어 실패한다. 프롬프트와 도구 계약에도 이 순서와 이유를 적었다.

## 전체 흐름

| 단계 | 실행 항목 | 확인 내용 |
| --- | --- | --- |
| 1 | On-Prem Agent 선택 | Local Qwen 실행 경로를 선택한다. |
| 2 | 자연어 요청 입력 | `acme/dev` 테넌트 경계와 선언된 애드온 설치를 요청한다. |
| 3 | 테넌트 구성 | Namespace 4개와 격리 정책 4축을 생성한다. |
| 4 | 애드온 설치 | 레지스트리의 chart, version, values를 읽어 Loki와 Tempo를 설치한다. |
| 5 | 대시보드 검증 | quota·network·RBAC·pod security와 애드온 상태를 확인한다. |
| 6 | ArgoCD 검증 | `acme-dev-logging`, `acme-dev-tracing`이 Synced/Healthy인지 확인한다. |
| 7 | 격리 반증 | NetworkPolicy를 제거·복구해 network 축만 정확히 바뀌는지 확인한다. |

## 시나리오

영상에서 사용한 요청은 다음과 같다.

```text
Stand up tenant acme in the dev environment on this cluster: create its isolation boundary and then install the add-ons it declares.
```

Local Qwen은 요청을 두 개의 도구 호출로 나눴다.

```text
setup_tenancy → install_tenant_addons
```

실행 후 `acme/dev`에는 네 개의 Namespace가 생겼다. 테넌트 전체 기준 CPU 16코어·메모리 64Gi·Pod 200개의 쿼터도 적용됐다. 로깅과 트레이싱 애드온은 각각 Loki 7.1.0과 Tempo 1.24.4로 설치됐다. 자연어 요청부터 도구 실행 완료까지 17.6초가 걸렸다.

공유 플랫폼 애드온은 에이전트의 작업 범위에서 뺐다. ArgoCD, Prometheus, Grafana, Capsule, Argo Rollouts처럼 클러스터 전체가 함께 쓰는 9개 구성요소는 Terraform이 계속 소유한다. 에이전트가 같은 객체를 Helm으로 다시 관리하면 한 리소스에 주인이 둘 생긴다.

## 무엇을 검증했나

### 자연어가 실제 작업으로 이어지는가

Local Qwen은 문장에서 테넌트, 환경, 작업 순서를 읽고 정해진 도구를 호출했다. 실행 후 대시보드에는 Namespace 4/4, quota, network, RBAC, pod security가 표시됐다. 선언만 만든 게 아니다. 각 클러스터 에이전트가 현재 상태를 허브로 보냈다.

### 애드온이 실제로 설치됐는가

대시보드에서 Loki와 Tempo가 각각 synced/healthy로 바뀌었다. ArgoCD에서도 `acme-dev-logging`과 `acme-dev-tracing`이 Synced/Healthy로 확인됐다. “설치 명령이 성공했다”는 기록에 그치지 않고 실제 GitOps 상태와 워크로드 상태를 함께 확인했다.

### 격리 상태를 믿을 수 있는가

정상 화면만 봐서는 상태를 믿기 어렵다. `acme/dev`의 NetworkPolicy 하나를 제거해봤다. 대시보드에서는 network 축만 빨간색으로 바뀌었다. quota, RBAC, pod security와 이웃 테넌트인 `globex/dev`는 그대로였다. 정책을 복구하자 network 축도 다시 정상으로 돌아왔다.

이렇게 화면의 초록색이 정적 데모 값이 아니라 클러스터에서 올라온 실측 상태임을 확인했다.

## 로컬 LLM을 붙이며 확인한 점

### 7B면 충분했다

라우팅 평가 20건에서 Qwen2.5-Coder-7B는 temperature 0 기준 20/20, Qwen3-Coder-30B는 19/20을 기록했다. 응답 시간은 각각 0.20초와 0.22초였다. 인프라 라우팅에서는 창의적인 문장보다 의도와 파라미터를 정확히 뽑아야 한다. 모델 크기보다 낮은 temperature와 명확한 도구 계약이 더 중요했다.

### 툴 콜 형식은 정규화가 필요했다

Qwen3-Coder가 `<function=...>` 형식으로 응답하면 MLX 서버와 클라이언트가 도구 호출을 인식하지 못할 때가 있었다. 응답을 OpenAI 표준 `tool_calls` 형식으로 바꾸는 프록시를 사이에 두었다. 모델 능력보다 출력 형식의 호환성 문제였다.

### 프롬프트 오류는 모델을 키워도 고쳐지지 않았다

초기 라우팅 정확도는 80%였다. 여러 모델이 같은 두 요청을 틀렸다. 원인은 프로비저닝의 범위를 잘못 설명한 프롬프트였다. 정의 한 문단을 고치자 정확도가 100%로 올랐다. 같은 요청을 여러 모델이 함께 틀린다면 모델보다 프롬프트와 도구 설명부터 살펴봐야 한다.

## 자동화에서 더 어려웠던 문제

가장 까다로운 문제는 에러가 나지 않는 실패였다. Namespace마다 16코어 쿼터를 걸어 팀 전체 한도가 64코어로 부풀거나, Pod Security가 워크로드를 거부했는데도 ArgoCD가 Synced로 표시되는 식이다. NetworkPolicy chart를 만들고 실제 설치 경로에 연결하지 않은 적도 있었다. 테스트는 모두 통과했지만 클러스터에서는 아무 일도 일어나지 않았다.

GitOps와 에이전트의 소유권 충돌도 풀어야 했다. 에이전트가 워크로드를 롤백해도 ArgoCD가 선언 상태로 복구하면 두 자동화가 서로를 되돌린다. 공유 리소스는 Terraform, 테넌트별 애드온은 GitOps가 맡고 에이전트에는 되돌릴 수 있는 운영 조치만 남겼다.

자연어 도구는 CLI와 달리 실행 직전에 컨텍스트를 눈으로 확인할 기회가 없다. 그래서 도구가 현재 kubectl context와 레지스트리의 대상 클러스터를 비교한다. 둘이 다르면 아무것도 쓰지 않고 요청을 거부한다.

## 실험 결과

Local Qwen은 자연어 요청 한 문장을 `setup_tenancy → install_tenant_addons`로 나눠 17.6초 안에 실행했다. Namespace 4개, 쿼터, NetworkPolicy, RBAC, Pod Security가 구성됐고 Loki와 Tempo도 ArgoCD에서 Synced/Healthy 상태에 도달했다. NetworkPolicy를 제거하고 복구했을 때 대시보드의 network 축만 바뀌는 것도 확인했다.

반복 작업은 분명 줄었다. 팀을 추가할 때 레지스트리 한 줄과 자연어 요청만 있으면 된다. 그렇다고 Kubernetes의 복잡성이 사라지지는 않는다. 쿼터 합산, 보안 정책, GitOps 소유권처럼 나중에 여러 번 마주칠 문제를 처음 설계할 때 미리 다루게 된다.

> 자동화는 러닝커브를 없애지 않는다. 앞으로 당긴다.

## 한계와 다음 단계

이번 검증은 로컬 kind 클러스터, 실 사용자 트래픽 없음, 테넌트 2개 조건에서 진행했다. 소프트 티어는 Namespace 수준의 격리이며 노드 CPU와 디스크 I/O 고갈까지 막지는 못한다. 공유 애드온 9개는 Terraform 소유라 에이전트 작업 범위에서 제외했다.

다음 단계로 적었던 세 가지는 이후 전부 처리됐다. 발행 시점의 계획을 그대로 두면 지금은 틀린 문장이 되므로, 결과를 함께 적는다.

| 발행 당시 "다음 단계" | 현재(2026-08-08) |
| --- | --- |
| agent→hub push 인증 | **완료**(2026-07-26). 무서명·틀린 키·신원 불일치·크로스테넌트 행 전부 401. |
| 서명키 보관과 교체 | **교체는 완료**(2026-08-08). 막고 있던 건 암호가 아니라 배포 위상이었다 — 서명자와 검증자가 다른 프로세스라 키 교체가 원자적일 수 없고, 그 실패가 "위조"로 보였다. 검증 전용 키 목록과 승인 TTL로 겹침 창을 유한하게 만들어 해결했다. **보관(custody)은 미해결** — 시크릿 매니저 선택이라 인프라 결정이다. |

읽기 경로에는 아직 구멍이 남아 있다. 쓰기는 허브가 막지만, 스포크가 클러스터를 **읽을 때**는 자격증명이 경계가 아니다. 테넌트 구분이 코드 안의 필터라서, 이걸 닫으려면 에이전트를 클러스터 안에 배포하는 일이 먼저다.

그다음에는 vCluster와 전용 클러스터 티어에서도 같은 계약과 검증 방식이 유지되는지 확인할 계획이다. 격리 수준을 어디까지 올릴 수 있는지는 발행본에 정리해 둔 표가 있다.

| 격리 수준 | 구성 방식 | 분리되는 범위 | 남는 공유 영역 | 적합한 경우 |
| --- | --- | --- | --- | --- |
| **네임스페이스** | Namespace + RBAC + NetworkPolicy + ResourceQuota | 리소스·권한·네트워크 | 제어 영역, 노드, 커널 | 신뢰할 수 있는 내부 팀 |
| **가상 클러스터** | 테넌트별 vCluster, 노드는 공유 | Kubernetes API·CRD·제어 영역 | 실제 워커 노드와 커널 | 팀별 독립된 Kubernetes 환경이 필요할 때 |
| **전용 노드** | 테넌트별 Node Pool 또는 vCluster Private Nodes | CPU·메모리·노드 장애 범위 | 상위 클러스터의 제어 영역 | 노이즈 네이버, GPU, 성능 간섭을 줄여야 할 때 |
| **전용 클러스터** | 테넌트별 Kubernetes 클러스터 | 제어 영역과 워커 노드 전체 | 클라우드 계정·네트워크는 선택적으로 공유 | 외부 고객, 규제 환경, 강한 보안 경계 |
| **전용 인프라** | 전용 클러스터 + 별도 계정/VPC + 전용 호스트 또는 베어메탈 | 클라우드와 물리 서버까지 | 사실상 없음 | 금융·공공·국방 등 물리적 격리가 필요한 경우 |

이번에 검증한 것은 첫 줄, 네임스페이스 수준이다.
